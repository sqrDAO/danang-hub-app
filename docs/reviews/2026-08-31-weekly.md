## 3. Findings

### H-1 — `autoApproveDeskBooking` reads capacity and writes approval outside a transaction, so concurrent desk bookings can be auto-approved past capacity

`functions/index.js:1940-1962`. On booking creation, this trigger reads current bookings for the amenity via `computeBookingAvailability` and, if it finds no conflict, writes `status: "approved"` directly — no `runTransaction`. Two bookings created for the same desk at (or overlapping) the same time, close enough together that both triggers read before either writes, will each see `hasConflicts: false` and both get auto-approved, oversubscribing the amenity's declared `capacity`. `AMENITY_TYPES_WITH_CAPACITY_CONCURRENCY = ["desk"]` makes desks the one amenity type this matters for — every other type is single-occupancy and this same function only auto-approves non-desk bookings when there's no conflict at all, so the race is desk-specific. This is the identical bug class `autoPromoteWaitlist` (`functions/index.js:2490-2521`) already had and was fixed for in PR #48 (`db.runTransaction`, re-reading attendees/waitlist/capacity inside the transaction) — that fix was never mirrored onto this sibling function, which is the one place server-side capacity enforcement for desks is supposed to be authoritative (client-side `checkBookingConflicts` is documented-advisory and swallows errors; `firestore.rules` does not enforce capacity at all). Concrete consequence: two members booking the last available desk slot within the same few hundred milliseconds (a plausible coworking-space pattern — a popular slot opening or two people booking right after standup) can both end up `approved` for a desk `capacity` already says is full, with no error to either member and no record that anything went wrong. Spec: `docs/backlog/todo.transact-auto-approve-desk-booking.md`.

### M-1 — Waitlist promotion, automatic or admin-triggered, never notifies the promoted member

`functions/index.js:2523` (`autoPromoteWaitlist`) — a literal `// TODO: Notify promoted members` next to a `console.log`, no notification call. `src/services/events.js:436-470` (`promoteFromWaitlist`, the admin-manual equivalent called from `src/pages/admin/Events.jsx:259`) has the identical gap — it transactionally moves members from `waitlist` to `attendees` and returns a count, with no notification anywhere in the surrounding admin UI either. Concrete consequence: a member who joined an event waitlist, then gets promoted to a confirmed attendee (because someone else cancelled, or because an admin manually promoted them), gets zero in-app notification, push, or email about it — they only find out by revisiting `/member/events`. `sendEventReminders` (24h-out) will eventually surface them as an attendee, but only if the promotion happened more than 24h before the event; a same-day promotion (the case a waitlist is most useful for) never reaches them at all. Spec: `docs/backlog/todo.notify-promoted-waitlist-members.md`.

### M-2 — `sendEventReminders`'s per-recipient notification writes aren't error-isolated, so one failing write silently drops reminders for every other event in that hourly run

`functions/index.js:1764-1780` (`deliverReminderSegment`). The `Promise.all(docs.map(...))` over `createNotificationIfAbsent` calls has no try/catch — only the push-send call directly below it (lines 1785-1807) is wrapped. `createNotificationIfAbsent` (`functions/index.js:757-775`) rethrows any Firestore error that isn't `ALREADY_EXISTS`. Because `sendEventReminders` (`functions/index.js:1814-1883`) iterates approved events in a plain `for` loop calling `deliverReminderSegment` per segment per event, one member's notification-create failing for any reason (transient Firestore error, quota) throws out of the loop and is caught only by the single outer try/catch wrapping the entire scheduled run — every event/segment not yet reached in that hour's iteration order is silently skipped. Since the reminder window is a fixed, freshly-recomputed 24-25h band with no retry queue, those members permanently miss the reminder for that event occurrence; the only trace is one `console.error`. This is exactly the failure shape #81 (this same window) fixed in `autoCheckoutExpiredBookings` by isolating each query/step — the same fix was needed here but wasn't applied, likely because #63 and #81 were separate PRs weeks apart. Spec: `docs/backlog/todo.isolate-event-reminder-errors.md`.

### M-3 — Desktop browser push is never disabled on logout for members who opted in before push was restricted to mobile

`src/services/pushNotifications.js:347-351`:
```js
export const disablePushNotificationsOnLogout = async (uid) => {
  if (!isMobilePushEligible()) return false
  await disablePushNotifications(uid)
  return true
}
```
Called from `src/contexts/AuthContext.jsx:151-158` on logout, but only when `isMobilePushEligible()` is true. Before PR #54 (this window), browser push was available on any device; members who opted in from a desktop browser prior to that PR have `preferences.pushNotifications: true` with a live token in `push_tokens/{uid}`. After #54, this cleanup function returns early on non-phone devices without ever calling `disablePushNotifications`, so the stored token is never deleted and the FCM subscription in that browser stays live — independent of the app's logged-in session. Concrete consequence: on a shared or kiosk desktop in the coworking space (a real fixture — the Hub has shared machines), a member who logs out continues receiving their own booking/event push notifications on that shared browser indefinitely, until the token naturally goes stale or someone manually disables it via the Profile "registered phone" toggle. Spec: `docs/backlog/todo.disable-desktop-push-on-logout.md`.

### M-4 — Hub closure dates are enforced for Event Hall bookings but not for events that don't request an amenity

`functions/eventLifecycle.js:66-82` (`getEventSpaceValidationError`, the only server-side closure check for events) is called from `reviewEvent` only inside `if (action === "approved" && initialData.requestedAmenityId)` (`functions/index.js:448`). An organizer who submits an event without checking "Request Event Hall" gets zero closure validation anywhere — not client-side (`src/pages/member/Events.jsx` and `src/services/events.js` have no closure reference at all, confirmed by grep) and not server-side. The closure notice copy itself (`en.json` `closures.noticeHint`) claims "Bookings and events cannot be made on these dates," which is false for this path, and the notice isn't even surfaced on the Events pages. Concrete consequence: an admin can approve, and a member can attend, an event scheduled for a day the Hub has declared closed — the same admin/member surface where closures are supposed to be authoritative for bookings has a silent exception for amenity-less events. Spec: `docs/backlog/todo.enforce-hub-closure-for-all-events.md`.

### M-5 — Same-day/"is this today" checks use the browser's local calendar day instead of Hub (Asia/Ho_Chi_Minh) time

Three independent spots use `Date.prototype.toDateString()` or local `setHours(0,0,0,0)` instead of the codebase's own `src/utils/timezone.js` (`isSameHubDay`, `getHubStartOfDay`) or the pattern already used correctly one file over in `src/pages/admin/Dashboard.jsx:268-269` (`toLocaleDateString('en-CA', {timeZone: 'Asia/Ho_Chi_Minh'})`):
- `src/services/bookings.js:225,241,305` — `checkIn`/`checkOut` reject with "only allowed on the same day as the booking" using local-day comparison.
- `src/pages/admin/Bookings.jsx:58-62,79-84,150-176` — `getTodayStart`/`isSameDayAsBooking` gate the Check In/Check Out buttons and the default "hide past bookings" filter.
- `src/pages/member/Dashboard.jsx:31-36,300-309` — `getTodayStart` splits a member's own upcoming vs. past bookings.

This directly conflicts with the "Everything is Asia/Ho_Chi_Minh" invariant. Concrete consequence: an admin or member whose device timezone trails Vietnam (any Americas or most European zones) will, for several hours after Vietnam midnight, have today's bookings mis-treated as "yesterday" — Check In/Check Out is disabled with the "same day" error for a booking that has already started in Hub time, it's hidden under "past" in the admin list, and it drops off the member's own "Upcoming" list. Devices ahead of Vietnam see the opposite: stale bookings still shown as actionable. Spec: `docs/backlog/todo.fix-same-day-checks-to-hub-timezone.md`.
