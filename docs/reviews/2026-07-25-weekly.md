## 3. Findings

Severity: **H**igh = data integrity / access control · **M**edium = user-visible
defect or ongoing cost · **L**ow = quality, no user impact.

### H-1 · Event registration is not permitted by the committed rules

`firestore.rules:95` is the only non-admin update path on `events/{eventId}`:

```text
allow update: if isAuthenticated() && isOwner(resource.data.organizerId);
```

But `registerForEvent`, `unregisterFromEvent`, `addToWaitlist` and
`removeFromWaitlist` (`src/services/events.js:290-336`) all write `attendees` /
`waitlist` directly via `updateDoc`. A member who is *not* the organizer matches
neither `allow update` clause, so every registration should fail
`permission-denied`. `docs/knowledge/data-flow.md:189` states the same rule shape,
so this is not a doc/code mismatch — the rules genuinely have no attendee-write path.

Either registration is broken for everyone except organizers and admins, or the
deployed ruleset is looser than `firestore.rules` in git. Both are serious and the
second is worse.

**Confirmed blocking gate**: nobody touches the events rules until the deployed ruleset
is diffed against git. That is step 0 of the spec, with the exact commands — it needs
credentials this review did not have (`firebase` CLI absent, `.firebaserc` gitignored,
and the service account lives in the `FIREBASE_SERVICE_ACCOUNT_DANANG_HUB_APP` GitHub
secret), so it is a human step.

→ spec: `docs/backlog/todo.event-rules-attendee-writes.md`

### H-2 · An organizer can approve their own event

The same rule places no field restrictions on organizer updates, and
`createEvent` (`src/services/events.js:100`) passes `status: data.status || 'pending'`
straight through while the create rule (`firestore.rules:93`) only checks
`organizerId`. So a member can set `status: 'approved'` on their own event — at
create time or afterwards — and skip admin review entirely. The write also fires
`notifyEventStatusChange`, so the hub sends a genuine "your event was approved"
email for an event no admin ever saw. The organizer can likewise rewrite
`attendees`, `capacity` and `date` on an approved event.

Compare `bookings`, which pins member creates to `status == 'pending'` and allows
owners only the `cancelled` transition. Events need the same treatment.

→ spec: `docs/backlog/todo.event-rules-attendee-writes.md` (same rules block; one PR)

### M-1 · Unapproved events are shown publicly as registerable

`getUpcomingEvents()` (`src/services/events.js:107`) merges `status == 'approved'`
with `status == 'pending'`. Its callers filter by date only — never by status —
including the two anonymous-visitor surfaces: `src/pages/Home.jsx:187` and
`src/pages/Events.jsx:282`. The public card (`src/pages/Events.jsx:328`) renders a
pending event under "Upcoming Events" with a title, organizer, date and a
**Register** button, visually identical to an approved event.

So any member's draft request advertises itself on the homepage before an admin
looks at it, and clicking Register on it hits H-1. The `getUpcomingEvents` docstring
claims it will "filter by date in memory" — no date filter exists in the function;
all four callers reimplement it.

Note `src/pages/Events.jsx:281` carries the comment "(approved and pending)", so
someone knew. **Decision settled 2026-07-25: pending events must not preview publicly** —
approved-only on anonymous surfaces, members keep seeing pending on `/member/events`. The
spec is unblocked and ready to build.

→ spec: `docs/backlog/todo.public-events-approved-only.md`

### M-2 · Waitlist promotion is not atomic, and drops concurrent joins

Two implementations, same bug:

- `promoteFromWaitlist` (`src/services/events.js:343`) — `getDoc`, compute, then
  `updateDoc({ attendees: arrayUnion(...promoted), waitlist: remaining })`.
- `autoPromoteWaitlist` (`functions/index.js:1541`) — same shape off the trigger
  snapshot.

Both write `waitlist` as a whole array built from a stale read. Anyone who joins
the waitlist between the read and the write is silently erased — no error, no trace,
they simply never get promoted. The two paths can also race each other: an admin
clicking "promote" while a member unregisters can double-promote past `capacity`,
since neither re-checks under a lock. `arrayUnion` protects `attendees` from
duplicates but not from overflow.

Both need `runTransaction` re-reading the doc inside the transaction.

→ spec: `docs/backlog/todo.atomic-waitlist-promotion.md`

### M-3 · Two deployed Cloud Functions do nothing

- `updateEventCapacity` (`functions/index.js:1352`) — fires on **every** `events`
  update, `JSON.stringify`-diffs the attendees array, and on a full event
  `console.log`s "is now full". No write, no notification, no return value used.
  Every registration, waitlist change and admin edit pays an invocation.
- `cleanupOldBookings` (`functions/index.js:1374`) — daily schedule; queries up to
  100 completed bookings older than 30 days and logs each one. The body comment
  says "Optionally delete or archive"; nothing is deleted or archived. The name and
  the README entry both promise cleanup that does not happen.

Delete them, or implement what they claim. Right now they are cost plus a false
entry in the functions table.

→ spec: `docs/backlog/todo.remove-noop-functions.md`

### M-4 · `verifyWalletSignature` skips the validation its sibling does

`generateWalletNonce` (`functions/index.js:1405`) whitelists
`chain ∈ {ethereum, solana}` and regex-validates the address before writing
`nonces/{address}`. `verifyWalletSignature` (`functions/index.js:1452`) checks only
that both are truthy. Consequences:

- `chain: 'foo'` falls through both branches, leaves `uid` undefined, and
  `createCustomToken(undefined)` throws — surfacing as an opaque `internal` to the
  client **after** the nonce has already been consumed by the transaction, so the
  user must restart the whole signing flow.
- `address` is used unvalidated as a document id at `functions/index.js:1465`; a `/`
  in it throws inside the Firestore call rather than returning `invalid-argument`.

Not an impersonation risk — signature recovery still has to match, so an attacker
must hold the key. It is an input-validation and error-shape gap: reject early,
before the nonce is spent.

→ spec: `docs/backlog/todo.wallet-verify-input-validation.md`

### M-5 · Two public pages are English-only

`src/pages/Events.jsx` and `src/pages/Amenities.jsx` never call `useTranslation`.
Page titles, section headers, loading text, empty states and button labels are
hardcoded English ("Browse community events and register to attend", "No upcoming
events at this time", "Amenities"). These are the anonymous-visitor pages, so a
Vietnamese visitor's first impression of the hub is untranslated — while every
member-facing page is fully localized and `en.json`/`vi.json` are otherwise in
perfect parity.

`src/pages/admin/Amenities.jsx` has 9 hardcoded `showToast` strings on the same
grounds (lines 96, 153, 551, 554, 564, 567, 575, 583, 649) — smaller, admin-only.

→ specs: `docs/backlog/todo.i18n-public-pages.md`,
`docs/backlog/todo.i18n-admin-amenities-toasts.md`

### L-1 · `useInvalidateQueries` returns an unmemoized closure

`src/hooks/useInvalidateQueries.js:6` builds a new function every render. Harmless
today — all nine call sites use it inside mutation `onSuccess`, none in a dependency
array. But it is exactly the shape someone will later drop into a `useEffect` dep
list and get an infinite loop from. One `useCallback` closes it permanently.

### L-2 · The calendar's bookings error is now fully silent

PR #25 removed the dead React Query v4 `onError` from
`src/components/UnifiedCalendar.jsx:96`. Correct — v5 ignores it, so the
`console.error` never ran. But the query still destructures neither `error` nor
`isError`, so a failed bookings fetch renders as an empty calendar with no signal to
the user or the console. The sibling `events` query has the same shape. Worth a
surfaced error state, not just a restored log.

### L-3 · The new lint guard has three gaps

`.eslintrc.cjs:42` matches an `ArrayExpression` as the first argument, which catches
`invalidateQueries(['bookings'])`. It does not catch `invalidateQueries(someKeyVar)`,
`invalidateQueries(['bookings'], options)` in the arg position it checks, or a bare
`invalidateQueries()` — which invalidates the entire cache and is the most expensive
version of the bug it exists to prevent. Tightening the selector to "first argument
is not an ObjectExpression" would cover all three.
