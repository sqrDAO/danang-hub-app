## 3. Findings

### M-1 — `sendBookingConfirmation` has been a no-op since before this window

`functions/index.js:1677-1709`. The trigger computes `sendEmail` from the member's
`preferences.emailNotifications` and then only `console.log`s the booking details — the body
literally says `// TODO: Integrate with email service; only send if sendEmail is true`. Every
booking creates a Cloud Function invocation that does nothing but log. Members have never
received a booking confirmation email. Not introduced this window, but confirmed still true at
HEAD and it's exactly the "trigger that only logs" pattern the invariant sweep is meant to catch.
The fix is mechanical: `notifyEventStatusChange` (`functions/index.js:1857+`) already has a
working `getTransporter().sendMail(...)` pattern gated the same way — reuse it.
Spec: `docs/backlog/todo.implement-booking-confirmation-email.md`.

### M-2 — Event reminder push can double-send at the hourly boundary

`functions/index.js:1567-1591` (`deliverReminderSegment`) sends push to every doc in a segment
regardless of whether `createNotificationIfAbsent` actually created a new in-app row for that
member — `created` is computed but never used to filter the push call. Combined with
`sendEventReminders`'s window (`functions/index.js:1610-1615`, `date >= in24Hours && date <=
in25Hours`, both bounds inclusive) on an `every 1 hours` schedule, an event whose `date` lands
exactly on a run boundary (e.g. exactly 25h from the first run) is picked up by two consecutive
runs. The in-app notification is correctly deduped by `createNotificationIfAbsent`, but affected
members get the push twice.
Spec: `docs/backlog/todo.dedupe-event-reminder-push.md`.

### M-3 — Organizers get reminded to register for their own event

`functions/index.js:1487-1499` (`segmentReminderRecipients`) segments every member into
attendee/waitlisted/other by checking `attendees`/`waitlist` membership only. It never excludes
`eventData.organizerId`. Organizers are not auto-added to their own event's `attendees` array
(confirmed in `src/pages/member/Events.jsx`'s `buildEventData`), so every organizer lands in
"other" and gets the "spots open — register now" (or waitlist-open) push/notification for the
event they created, roughly 24h before it starts.
Spec: `docs/backlog/todo.exclude-organizer-from-reminders.md`.

### M-4 — A failed conflict check is invisible to the member

`src/pages/member/Bookings.jsx:375-396` (`handleContinueToConfirm`) wraps `checkBookingConflicts`
in try/catch and sets `conflictError` to `t('memberBookings.conflictCheckFailed')` on catch. But
`checkBookingConflicts` (`src/services/functions.js:6-21`) never throws — on any failure it
resolves `{hasConflicts: false, conflicts: []}` by design (CLAUDE.md: "advisory... returns
`{hasConflicts: false}` on error"). The catch branch is therefore dead code: a genuine backend
outage during the conflict check is silently treated as "no conflicts," and the member proceeds
straight to the confirm step with no indication the check never ran. The `conflictCheckFailed`
i18n string exists in both locales and is wired up in the UI — it just can never fire.
Spec: `docs/backlog/todo.surface-conflict-check-failure.md`.

### L-1 — Admin review errors give no way to recover without a manual refresh

`src/pages/admin/Events.jsx:235-254`. `approveMutation`/`rejectMutation`'s `onError` shows one
generic toast (`toast.eventApproveFailed`/`eventRejectFailed`) for every `reviewEvent` failure —
stale revision (`aborted`, e.g. the organizer edited the event mid-review), Hall no longer
available (`failed-precondition`), or the event has since started. No cache invalidation either,
so retrying hits the same stale cached `event.revision` and fails identically until the admin
manually reloads the page. The organizer-edit path already solved this exact problem
(`EVENT_EDIT_ERROR_KEYS` / `getEventEditErrorMessage`, `src/pages/member/Events.jsx:886-902`) —
this is the same fix, ported to the admin mutations.
Spec: `docs/backlog/todo.admin-review-error-messaging.md`.

### L-2 — Dead `dev:booking` script and a stale spec for a fully-reverted feature

The entire local-booking preview mode (`src/App.jsx` auth bypass, `Bookings.jsx` fixture
fallback, `BookingCalendar.jsx` skip-remote-reads, `src/utils/localBookingMode.js`) was
implemented in `5bfaf3f` and then completely removed six commits later in `876d869` ("fix:
support per-day amenity availability in booking calendar"), which deleted
`localBookingMode.js` and its `App.jsx`/`Bookings.jsx` wiring outright. `package.json:8`'s
`"dev:booking": "vite --mode booking"` script survives as a no-op (nothing checks
`import.meta.env.MODE === 'booking'` anymore), and `docs/backlog/todo.local-booking-dev.md` is
still open, describing a feature that no longer exists.
Spec: `docs/backlog/todo.remove-dead-local-booking-dev.md`.

### L-3 — Shared-desk capacity check duplicated between client and server with no cross-reference

`src/components/BookingCalendar.jsx:500` hardcodes `isSharedDesk = amenity?.type === 'desk' &&
capacity > 1`, duplicating the server's canonical `AMENITY_TYPES_WITH_CAPACITY_CONCURRENCY =
["desk"]` (`functions/index.js:60`). The two lists agree today, but nothing keeps them in sync —
`functions/` and `src/` are separate deploy targets so a single shared import isn't free, but at
minimum the client-side logic should live in one place (`src/services/amenities.js`, which
already owns amenity-type defaults) with a comment cross-referencing the server list.
Spec: `docs/backlog/todo.centralize-shared-desk-check.md`.

### L-4 — Push notification content derivation copy-pasted between foreground and service worker

`src/services/pushNotifications.js` (`resolvePushContent`, and the `HUB_ICON`/`HUB_BADGE`/
`DEFAULT_PUSH_TITLE` constants) duplicates logic and constants that also live in
`public/sw.js:17-39`. In sync today; nothing enforces it stays that way, and this is exactly the
kind of foreground-vs-background divergence PR #53 was fixing.
Spec: `docs/backlog/todo.share-push-content-constants.md`.
