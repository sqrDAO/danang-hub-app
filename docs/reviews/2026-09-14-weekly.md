**i18n parity note**: the flat key-diff script flags `memberBookings.modal.durationHours_one`
and `durationMinutes_one` as "missing in vi." This is a false positive, not a finding —
`en.json` carries CLDR `_one`/plain-plural pairs (`durationHours_one` = "1 hour",
`durationHours` = "{{count}} hours") because English has a singular plural category;
Vietnamese has none (CLDR: `vi` is plural-invariant), so `vi.json` correctly uses the bare
`durationHours`/`durationMinutes` key for every count and has zero `_one` keys anywhere in
the file (verified: `grep -c '_one' vi.json` → 0). i18next's built-in pluralizer resolves
`t('durationHours', {count:1})` in the `vi` locale straight to that one key. No action
needed; the parity checker itself doesn't account for per-locale plural categories.

## 3. Findings

### H-1 — `reviewEvent`'s Event Hall availability check runs outside the transaction that books it, allowing a real double-booking

`functions/index.js:448-478` (availability check, outside any transaction) vs.
`:480-537` (the `db.runTransaction` that creates the linked booking).

```text
if (action === "approved" && initialData.requestedAmenityId) {
  ...
  const availability = await computeBookingAvailability({...});   // read #1, no lock
  if (availability.hasConflicts) { throw ... }
}

return await db.runTransaction(async (tx) => {
  const eventSnap = await tx.get(eventRef);                        // only re-reads the event
  ...
  const bookingQuery = db.collection("bookings").where("eventId", "==", eventId);
  const bookingSnapshot = await tx.get(bookingQuery);               // scoped to THIS event only
  ...
  tx.create(bookingRef, { amenityId: event.requestedAmenityId, startTime, endTime, ... });
```

The transaction re-reads the event doc (for the revision check) and queries bookings
**scoped to this event's own `eventId`** — it never re-reads bookings for the *amenity and
time window* it's about to book. Two admins approving two different pending events that
both request the Event Hall for an overlapping time window can both pass the
outside-transaction `computeBookingAvailability` check (neither has created a booking yet
when the other reads), then both `tx.create` an `approved` booking for the same amenity
and overlapping time. This is not the documented advisory-conflict gap
(`checkBookingConflicts` fail-open by design) — Event Hall is enforced single-occupancy
per CLAUDE.md ("every other type is single-occupancy" besides desks), and this path is the
one CLAUDE.md and `docs/knowledge/data-flow.md:155` describe as atomic
("...cannot be best-effort", "atomically creates at most one...booking"). The transaction
guarantees revision consistency on the event doc; it does not guarantee amenity-slot
exclusivity. Concrete failure: two organizers each request the Event Hall for
Friday 18:00–20:00 in separate events; an admin approves both within the same few
seconds (plausible on a pending-events review queue) — both bookings are created,
both events show as approved, and the Hub double-books its one shared event space with no
error to either admin. Spec: `docs/backlog/todo.reviewevent-transactional-availability-check.md`.

### M-1 — Members auto-promoted (or admin-promoted) off a waitlist are never notified

`functions/index.js:2523` — `autoPromoteWaitlist`'s transaction correctly moves members
from `waitlist` to `attendees`, but the line right after the transaction commits is only
`// TODO: Notify promoted members` backed by a `console.log`. The admin-triggered manual
path, `promoteFromWaitlist` (`src/services/events.js:436-461`), has the identical gap — it
runs its own client-side `runTransaction` with no notification step at all, and per
`firestore.rules:158` ("Only Cloud Functions...create notifications — no client-side
create") it couldn't write one even if it tried. Concrete failure: a member joins a
waitlist, later gets bumped into `attendees` because someone else cancelled (or an admin
manually promotes them), and has no signal — no in-app notification, no push — that they
now have a confirmed spot, until they happen to reopen the event. Spec:
`docs/backlog/todo.notify-waitlist-promotion.md`.

### M-2 — Rejecting a previously-approved event leaves the public `approvedEvents` cache stale

`src/pages/admin/Events.jsx:247-256` (`rejectMutation.onSuccess`) invalidates
`('events', 'pendingEvents', 'myEvents', 'upcomingEvents', 'bookings')` — missing
`'approvedEvents'`. The sibling `approveMutation` (`:236-245`) does invalidate it. But
`reviewEvent` explicitly allows rejecting an **approved** event, not just a pending one
(`functions/index.js:501-505`, `action === "rejected" && ["pending","approved"].includes(...)`).
Concrete failure: an admin rejects an already-approved event (e.g. a policy violation
surfaces after approval); the shared `['approvedEvents']` React Query cache — populated by
`getApprovedEvents()` and read by both the public `/events` page and Home's event list —
keeps serving the stale "still approved" version until an unrelated refetch happens, so
anonymous visitors and members can keep seeing and registering for an event the admin just
rejected. Spec: `docs/backlog/todo.fix-reject-approvedevents-invalidation.md`.

### M-3 — Public Home and Amenities pages render raw, untranslated amenity-type slugs

`src/pages/Home.jsx:179` (`<p className="amenity-preview-type">{amenity.type}</p>`) and
`src/pages/Amenities.jsx:133` (`<span className="amenity-type">{amenity.type}</span>`)
both render the raw Firestore `type` field (`meeting-room`, `podcast-room`, `event-space`,
`desk`) with no `t()` call. The `amenityTypes.*` i18n namespace already exists in both
locales (`en.json:382-387`, `vi.json:382-387`) and is used correctly elsewhere
(`src/components/UnifiedCalendar.jsx:375`, `src/pages/admin/Bookings.jsx:851`, both via
`t(\`amenityTypes.${type}\`, ...)`). Concrete failure: a Vietnamese-locale visitor to the
public homepage — the most-visible surface in the app — sees English amenity-type slugs
like "meeting-room" instead of "Phòng họp", while every other page in the app localizes
the same field. Spec: `docs/backlog/todo.i18n-public-amenity-type.md`.

### M-4 — Admin check-in/check-out compare dates in the browser's local timezone, not the hub's

`src/services/bookings.js:225` and `:241` (`checkIn`/`checkOut`) both do
`bookingDate.toDateString() !== today.toDateString()` — `Date.prototype.toDateString()`
renders in whatever timezone the browser is running in, not `Asia/Ho_Chi_Minh`. These are
admin-only call sites (grepped for callers; no member-page usage), so this isn't a rules
gap, but it violates CLAUDE.md's "Everything is Asia/Ho_Chi_Minh" invariant, and the fix
already exists and is unused here: `isSameHubDay()` (`src/utils/timezone.js:232-234`).
Concrete failure: an admin operating from a browser set to UTC or US time near the hub-day
boundary (e.g. 6–7am Vietnam time, still "yesterday" in UTC) can have a legitimate
same-hub-day check-in rejected, or — the opposite direction near midnight hub time — a
check-in/out for the wrong calendar day incorrectly allowed. Spec:
`docs/backlog/todo.fix-checkin-checkout-hub-timezone.md`.

### L-1 — Dead, non-transactional `approveEvent`/`rejectEvent` still exported from the service layer

`src/services/events.js:312-329`. Repo-wide grep confirms no caller anywhere —
`src/pages/admin/Events.jsx` correctly uses the `reviewEvent` callable instead. These two

inconsistent event/booking state with no error surfaced. Spec:
`docs/backlog/todo.remove-dead-approve-reject-event.md`.
