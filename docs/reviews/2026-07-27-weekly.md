## 3. Findings

### H-1 — Organizer can delete a live, approved event with no rules guard

`firestore.rules:122-123`:

```text
// Organizers can delete their own events
allow delete: if isAuthenticated() && isOwner(resource.data.organizerId);
```

Unlike `bookings`, where owner delete is rules-restricted to `status == 'pending'`
(`firestore.rules:84-85`, matching the documented invariant "owners can only set
cancelled... and delete only while pending"), the `events` delete rule has no status
check at all. `deleteEvent` (`src/services/events.js:310-313`) is a bare `deleteDoc` with
no status guard either. The member UI (`src/pages/member/Events.jsx:471-479`) only
renders the delete button when `event.status === 'pending'`, so the gap is invisible in
normal use — but nothing stops a organizer from calling `deleteEvent(id)` directly (devtools
console, a modified client, or a future code path that reuses the service function) on
their own **approved** event that already has registered attendees and a waitlist,
permanently erasing the event doc and every attendee's registration with no
notification, no audit trail, and no recovery. This predates this week's diff (the rule
line is unchanged since the initial commit) but is exactly the kind of gap the invariant
sweep is meant to catch, and it sits right next to the `events` rule this week's #49
already touched. Spec: `docs/backlog/todo.restrict-event-delete-to-pending.md`.

### M-1 — Register/waitlist cache patch writes the wrong query key, so the member's own Upcoming Events / Dashboard lists go stale

`src/pages/member/Events.jsx:260` (`EVENT_LIST_KEYS = ['approvedEvents', 'upcomingEvents']`)
and `patchEventInCaches` (line 273), called from the four mutation `onSuccess` handlers at
lines ~311, ~329, ~345, ~360.

The live query for this page's own "Upcoming Events" list is registered under
`['upcomingEvents', 'withPending']` (line 192; the same key is used by
`src/pages/member/Dashboard.jsx:290`), with a comment claiming it is "a prefix match of
`['upcomingEvents']`, so the existing invalidate calls still refresh both" — true for
`invalidateQueries` (fuzzy match on key prefix), but PR #50 replaced those invalidations
with `queryClient.setQueryData(['upcomingEvents'], ...)`, and `setQueryData` does an
**exact** key match. It writes a cache entry under the literal key `['upcomingEvents']`,
which no active query is subscribed to, and never touches `['upcomingEvents',
'withPending']`. Concrete failure: a member clicks "Register for Event," gets the
success toast, but the button still reads "Register for Event" and the attendee count on
this page (and on `/member` Dashboard) doesn't update until the window loses and regains
focus or the component remounts. Not a data-integrity issue — the underlying write is an
idempotent `arrayUnion`/`arrayRemove` and a manual refresh shows the correct state — but
a real, reproducible regression introduced by this week's perf change. Same gap applies
to waitlist join/leave. Spec: `docs/backlog/todo.fix-event-cache-patch-key.md`.

### M-2 — `common.saving` i18n key doesn't exist; three Save buttons render the raw key

`src/pages/admin/Amenities.jsx:402`, `src/pages/admin/Members.jsx:67` (both new this
week, PRs #42/#31), and `src/pages/admin/Events.jsx:726` (pre-existing, unrelated to this
week but the same missing key). All three call `t('common.saving')`. Neither
`en.json` nor `vi.json` defines `common.saving` — the only `saving` key in either locale
file is `profile.saving` ("Saving…" / "Đang lưu…"), and `common.saving` isn't there
(`common` has `save` but not the `-ing` form). i18next has no `missingKeyHandler` or
`defaultValue` configured, so a miss renders the literal string `common.saving`.
Concrete failure: an admin editing a member, saving an amenity, or saving an event sees a
button labeled `common.saving` for the duration of the mutation, in both locales. Spec:
`docs/backlog/todo.add-common-saving-i18n-key.md`.

### M-3 — `sendEventReminders` is a third no-op scheduled function, missed by this week's cleanup

`functions/index.js:1064-1121`. Runs hourly, queries events 24–25h out, resolves the
attendee list, filters by `preferences.eventReminders`, and — per its own inline comment
and the existing `docs/knowledge/data-flow.md` entry ("actual sending is TODO
(logs only)") — never emails or pushes anyone. It only `console.log`s a per-event summary
and a count. This is the same shape as the two functions PR #47 deleted this week
(`updateEventCapacity`, `cleanupOldBookings`) for exactly this reason — "both burned
invocations and both were advertised... as behavior that does not exist" — but
`sendEventReminders` is the one of the three that members can actually notice: the UI
almost certainly exposes an `eventReminders` preference toggle (the function reads
`preferences.eventReminders`), so a member who opted in and expects a reminder 24h before
an event they registered for never gets one. This needs a human decision — implement
real delivery, or delete it like its two siblings — so it's written up with a Decision
required section rather than a single-option spec. Spec:
`docs/backlog/todo.decide-event-reminders-fate.md`.

### M-4 — `.github/copilot-instructions.md` invents a Gemini AI chatbot integration that doesn't exist

`.github/copilot-instructions.md:20, 33-34` (introduced whole-file this week, `073c3c9`,
committed specifically to fix drift/stale facts in a previously-gitignored file). It
claims the stack includes "Google Gemini AI," lists a `src/services/gemini.js` described
as "Gemini agentic loop (max 10 iterations) with tool-calling," and describes
`checkSlotAvailability` as "used by the AI chatbot." None of this exists: there is no
`gemini.js` in `src/services/`, no `gemini`/`generative-ai` string anywhere in `src/`,
`functions/`, `README.md`, or `CLAUDE.md`, and no Gemini dependency in either
`package.json`. `README.md` and `docs/knowledge/data-flow.md` both correctly describe
`checkSlotAvailability` as a public availability check for the Amenities page, with no
chatbot mention. The commit's own message says its purpose was removing stale facts from
this exact file — this fabrication survived that pass. Concrete cost: this file is
committed specifically so Copilot sessions pick it up automatically; a future Copilot-
assisted change could import a nonexistent module or build around a chatbot that was
never built. Spec: `docs/backlog/todo.fix-copilot-instructions-gemini-claim.md`.

### L-1 — `handleCancelPlan` is the one action handler without the double-submit guard

`src/pages/member/Bookings.jsx:524-528`. Every other handler touched this week
(`handleCancel`, admin approve/reject/delete/promote, event register/unregister) got
`if (isPendingFor(mutation, id)) return`; `handleCancelPlan` didn't. Currently inert —
the triggering button is already `disabled={cancelPending}` and a disabled button doesn't
dispatch clicks — but it's the one inconsistency in an otherwise-complete pattern rollout
and worth aligning so the guard doesn't have to be re-derived if the button's disabled
logic ever changes. Spec: `docs/backlog/todo.add-cancel-plan-double-submit-guard.md`.
