## 3. Findings

### M-1 — Waitlisted event-reminder push aborts the rest of the segment on one failure

`functions/index.js:1239-1249`. For the waitlisted segment, `deliverReminderSegment`
sends push one recipient at a time inside a `for` loop, with the `try/catch` wrapping
the *whole loop*, not each iteration:

```js
if (segment === "waitlisted") {
  for (const doc of docs) {
    await sendPushToMembers([doc], { /* ... */ });   // can throw
  }
}
```

`sendPushToMembers` → `sendPushToRecipients` (`functions/index.js:708-717`) re-throws
after a failed `messaging.sendEachForMulticast` call (a transient FCM/network error, not
a per-token dead-token error — those are handled without throwing via
`isUnrecoverablePushTokenError`). When that happens on waitlisted member *N*, the
`for` loop stops — members *N+1..end* never get `sendPushToMembers` called for them at
all this run. Their in-app notification still lands (that `Promise.all` runs earlier,
line 1219, independent of the push loop), but the push reminder is silently skipped.

Because `sendEventReminders` selects events by a fixed 24–25h-out date window
(`functions/index.js:1281-1284`), a given event passes through that window on exactly
one hourly run. There's no later run that will pick it up again — a member who didn't
get their push this run never gets it. Concrete scenario: an event's waitlist has 15
members; member #4's send hits a transient FCM error; members #5–15 receive the in-app
notification (visible on next bell-open) but never the push nudge, with no log
distinguishing "skipped" from "sent."

Consequence: intermittent, silent under-delivery of the one feature this PR shipped to
fix ("people who have not registered still hear about it in time"), worse for larger
waitlists since each is a separate FCM call (more chances to hit a transient failure)
and the failure mode fans out to everyone after it in iteration order.

Spec: `docs/backlog/todo.isolate-reminder-recipient-failures.md`.
