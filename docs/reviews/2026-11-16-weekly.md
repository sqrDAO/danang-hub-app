## 3. Findings

No H or M findings.

- **L1 `emailNotifications` outlived its switch, and the log-only booking trigger now calls Auth.** #199 removed the email-notifications switch, but `src/contexts/AuthContext.jsx:70` still seeds the field and `functions/index.js:2307-2312` still reads it. `sendBookingConfirmation` now awaits `getVerifiedEmail` (`functions/index.js:2321`) only to `console.log` the result. That is one Auth Admin `getUser` per booking created: a 20-day fixed-desk plan makes 20 lookups and writes the member's verified email into Cloud Logging 20 times, and nothing uses it. The failure log in `getVerifiedEmail` (`functions/index.js:95`) is tagged `[event-status-email]` for every caller. `docs/knowledge/data-flow.md:89-90` still says the trigger reads the preference. → [#205](https://github.com/sqrDAO/danang-hub-app/issues/205)

Note without an issue, because it needs a decision first:

- **The verify gate can be bypassed by its owner.** The client writes `emailVerificationRequired` (`src/contexts/AuthContext.jsx:48`), and the owner `allow update` on `members` (`firestore.rules:70-73`) lets the owner delete it, so an unverified sign-up can skip the verify screen by writing to its own profile. `data-flow.md` already calls these guards "UX only", and mail never reaches an unverified address, so nothing is misdirected. If verification is meant to be a real requirement, rules would need to check `request.auth.token.email_verified` on booking and event creates (wallet accounts have no email, so they would need an exemption). Confirm whether UX-only is the intended policy.
