## 3. Findings

### M-1 — Admin-configured `slotDuration` is silently ignored by the new calendar grid

`src/components/BookingCalendar.jsx:33` hardcodes `CALENDAR_CELL_MINUTES = 30` and the
`availability` memo (`:400-404`) only reads `startHour`/`endHour`/`availableDays` — it
drops `slotDuration`, which the pre-rewrite calendar (base commit `43d951d`) read from
`amenity.slotDuration ?? DEFAULT_AVAILABILITY.slotDuration` to size the grid.

`slotDuration` is still a live, admin-facing field: `src/pages/admin/Amenities.jsx:368-373`
renders a form control for it, `:430` persists it, and `:206` displays "Slot: {duration}
min" on the amenity card. `EVENT_SPACE_AVAILABILITY` in `src/services/amenities.js:60`
defaults it to `60` for event-space amenities. Nothing downstream — not
`BookingCalendar.jsx`, not `bookingRange.js`, not `functions/index.js` — reads
`slotDuration` any more (`grep -rn slotDuration src functions` turns up only the
read/write in `amenities.js` and the admin form).

Concrete failure: an admin sets the event space to 60-minute slots (the default). A member
now sees a 30-minute-granularity grid and can book 18:00–18:30, a booking the admin's
setting was meant to prevent. The admin gets no error and no indication the field stopped
doing anything.

Spec: `docs/backlog/todo.restore-or-retire-slot-duration.md` (decision required).

### M-2 — Cells already inside a selected range don't re-validate against live availability

`src/utils/bookingRange.js`, `getSelectedCellState` (lines 67-98): once a cell matches the
selection's start (`:76-77`), end (`:80-84`), or interior (`:91-92`), its displayed status
is derived purely from its position in `[startMs, endMs)` — `cell.baseStatus` is never
consulted for those three branches. Contrast the "extend selection" branches
(`getCandidateState`/`getUnhighlightedCandidateState`, called from `:96-97`), which do call
`isRangeAvailable` and re-check live status.

Concrete failure: a member selects 9:00–11:00 on a shared desk. `allBookings` refetches
(any booking mutation elsewhere in the app invalidates the shared `'bookings'` prefix key,
or the window regains focus) and a slot inside 9:00–11:00 is now taken by someone else.
`baseStatus` for that cell flips to `booked`, but `getCellState` keeps returning
`range-selected`/`range-end` for it — the grid still paints the full range as a valid
selection. The final `checkBookingConflicts` call in `handleConfirmBooking`
(`src/pages/member/Bookings.jsx:407-424`) still bounces the booking on submit, so this is
a display bug, not a double-booking path — but it's exactly the failure mode the file's own
header comment (`BookingCalendar.jsx:523-526`, "never fall back to an empty booking
list... block selection instead") says the rewrite exists to avoid.

`test/bookingRange.test.js` has no case that changes `baseStatus` mid-selection, so this
regression (or its fix) is untested either way. Its only `'range-blocked'` case exercises
the single-cell candidate-extension path, not an established multi-cell selection.

Spec: `docs/backlog/todo.revalidate-selected-range-cells.md`.

### M-3 — `checkBookingConflicts`'s fail-open design leaves its own error handling unreachable

`src/services/functions.js:6-21`: `checkBookingConflicts` catches every error internally
and always resolves `{hasConflicts: false, conflicts: []}` — it never rejects. This is
CLAUDE.md's documented "advisory, fails open" design and is not new.

What's new this window: `handleContinueToConfirm` and `handleConfirmBooking`
(`src/pages/member/Bookings.jsx:371-392`, `:399-424`) were rewritten as part of the
range-picker work, and both still wrap the call in `try { ... } catch (error) { ...
form.setConflictError(t('memberBookings.conflictCheckFailed')) ... }`. Because the service
layer never rejects, these `catch` blocks — and the `conflictCheckFailed` copy they show —
are unreachable dead code. If the `checkBookingConflicts` Cloud Function is down or times
out, the member sees no warning at all and the booking proceeds as if verified clean,
silently relying on `firestore.rules` (which CLAUDE.md notes does **not** enforce overlap)
to catch nothing.

The same PR window established the opposite precedent on purpose: `getAmenityBookingRanges`
(`src/services/functions.js:32-41`) throws instead of swallowing, with a comment
explicitly contrasting it with `checkBookingConflicts` ("Deliberately unlike
`checkBookingConflicts` above: this one throws"). That comment shows the team is already
aware of the asymmetry; it just hasn't been resolved for the conflict check itself.

Spec: `docs/backlog/todo.checkbookingconflicts-failure-handling.md` (decision required).

Spec: `docs/backlog/todo.document-getamenitybookingranges.md`.

### L-2 — Desk capacity-concurrency rule duplicated client-side instead of shared

`src/components/BookingCalendar.jsx:448`: `const isSharedDesk = amenity?.type === 'desk'
&& capacity > 1`. The actual source of truth, `AMENITY_TYPES_WITH_CAPACITY_CONCURRENCY`
(`functions/index.js:56`, `["desk"]`), is server-only and never exported to the client.
The two agree today, so this isn't a live bug, but CLAUDE.md calls this array out as the
one invariant governing which amenity types allow capacity-based overlap — if it ever
grows, `BookingCalendar.jsx`'s grid and `bookingRange.js`'s peak-concurrency math won't
follow, and the UI will show availability the backend won't honor.

Spec: `docs/backlog/todo.share-capacity-concurrency-types.md`.

### L-3 — Dead CSS selector in the new range-status panel

`src/pages/member/Bookings.css:415-417`:

```css
.booking-range-actions,
.booking-range-status > .btn {
  width: 100%;

```

`.booking-range-status > .btn` never matches: in `BookingRangeStatus`
(`src/pages/member/Bookings.jsx:761-784`), every `.btn` is a grandchild of
`.booking-range-status` via the intermediate `.booking-range-actions` div, never a direct
child. Cosmetic only — the sibling `.booking-range-actions` selector on the same rule
already achieves the intended full-width-buttons-on-mobile effect.

Spec: `docs/backlog/todo.remove-dead-booking-range-css-selector.md`.

## 4. Incident note (already resolved, no action needed)

`fb16ca0` ("block booking selection on query failure...", 2026-08-06) correctly replaced
the old fail-open-to-empty-list behavior with a hard error panel when a member's booking
list failed to load — but `firestore.rules` only ever allowed a member to read their own
bookings, and `BookingCalendar` had always queried by `amenityId` (which no rule can
satisfy, since rules evaluate the query shape, not its results). That turned a
long-standing silent failure (empty list → every slot painted free) into a hard block:
between 2026-08-06T06:43Z and the stopgap fix, no non-admin member could see or make a
booking. `caed673` (2026-08-07) shipped a temporary `allow read: if isAuthenticated()`
rule on `bookings` — trading full schedule visibility across all members for a working
booking flow — followed the same day by `5253b3f`/`78c4d7f`, which shipped
`getAmenityBookingRanges` (anonymized occupancy only) and removed the temporary rule. Final
state (`firestore.rules:52-63`) is owner-only reads plus the callable, confirmed above (§2,
§3 L-1). Documented here because the temporary broad-read rule was live in production for
part of a day; no residual code or rule reflects it and no further action is needed.
